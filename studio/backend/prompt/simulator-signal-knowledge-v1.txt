Rules

* Never invent a meaning only because the name looks familiar.
* Use messageName only as context to disambiguate the signal, not as the returned signal name.
* If messageName contains CMD, COMMAND, CONFIG, LIMIT, MAX, MIN, CALIB, INIT, STATUS, DIAG or FAULT, treat the signal conservatively.
* Signals that represent limits, configured maximums, setpoints, calibration values, initialization values, diagnostic states, faults or internal controller status must be false for behavior generation unless the signal is clearly a direct measured physical quantity.
* Signals with names containing MAX, MIN, LIMIT, THRESHOLD, CONFIG, CALIB, INIT, SET_ME or SETME must normally be false for behavior generation unless the signal is clearly a direct measured physical quantity.
* If the signal is probably a protocol field, state that.
* If the signal appears to be:
    - Counter
    - Rolling counter
    - Checksum
    - CRC
    - Alive counter
    - Timestamp
    - Reserved field
    - Diagnostic field
    - Protocol bookkeeping
  mark it as false for behavior generation.

* If the physical meaning cannot be inferred with reasonable confidence, set: "generateBehavior": false


Behavior suitability

generateBehavior
true : only if the signal represents a physical quantity or physical state that naturally evolves during vehicle operation.
Examples:
- VehicleSpeed
-  BrakePressure
- BrakeLights
- BatteryVoltage
- MotorTemperature
- AcceleratorPedal
- SteeringAngle
- YawRate
- WheelSpeed

generateBehavior
false : for signals that should not be directly generated as physical behavior, including:
- Counters
- Checksums
- CRCs
- Alive fields
- Protocol status
- Reserved values
- Diagnostic information
- Frame bookkeeping
- Timing information
- Unknown signals
- Configuration or command limit signals
- Diagnostic fault or error status signals
- Calibration or initialization fields

Dependency
- Only reference another signal that exists in the provided signal list. 
- Check all signals for physicall dependencies.
- Use dependency when there is a strong physical, logical, or causal relationship between two provided signals.
- Prefer null only when no meaningful relationship exists.
- Do not use null just because the relationship is not mathematically exact.
- Never create circular dependencies.
- Prefer primary physical quantities as dependency sources.
- Speed, pedal, torque, steering angle, brake application and vehicle motion signals should normally be dependency sources, not dependent on secondary sensors.
- Examples of signal dependencies:
    "Brake_Lights" -> "Brake_Drv_Appl"
    "WhlFr_W_Meas" -> "LKASVehicleSpeed"
    "LEFT_HALL_SENSOR" -> "SPEED_L"
    "RIGHT_HALL_SENSOR" -> "SPEED_R"
    "Hands_Warning" -> "LaHandsOff_B_Actl"

Validation

Before returning JSON verify:
- Valid JSON.
- Every requested signal appears exactly once.
- No extra signals.
- generateBehavior is boolean.
- Unknown signals are marked with low confidence.
- No invented signal names.
- No invented DBC information.
- Do not copy messageName, canId, dbcFile, unit, min, max, factor, offset or bit length into the output.
- No markdown.
- No explanations or any character outside valid JSON.
