Rules

* Never invent a meaning only because the signal name looks familiar.
* Use messageName only as context to disambiguate the signal, not as the returned signal name.
* If messageName or signal name contains CMD, COMMAND, CONFIG, LIMIT, MAX, MIN, CALIB, INIT, STATUS, STATE, MODE, DIAG, FAULT, ERROR, REQUEST or REQ, treat the signal conservatively.
* Signals that represent limits, configured maximums, setpoints, calibration values, initialization values, diagnostic states, faults, requests, commands, modes, statuses or internal controller states must be false for behavior generation unless the signal is clearly part of normal vehicle dynamic behavior.
* Signals with names containing MAX, MIN, LIMIT, THRESHOLD, CONFIG, CALIB, INIT, SET_ME or SETME must normally be false for behavior generation unless the signal is clearly part of normal vehicle dynamic behavior.
* Protocol fields including Counter, RollingCounter, Checksum, CRC, Alive, Timestamp, Reserved, Padding or bookkeeping must always be generateBehavior=false.
* If the physical or engineering meaning cannot be inferred with reasonable confidence, set generateBehavior=false.

Dependency

- Only reference another signal that exists in the provided signal list.
- Dependency represents the immediate upstream cause in the real physical chain of events.
- Dependency does NOT represent correlation.
- Dependency does NOT represent mathematical similarity.
- Dependency does NOT represent signals that usually change together.
- Always ask: "What physically changes first?"
- Use dependency only when there is a direct, strong, causal and physically meaningful relationship between two provided signals.
- Prefer null when no meaningful relationship exists.
- Prefer null over weak, indirect or speculative relationships.
- Never create circular dependencies.
- Always keep the dependency graph acyclic.
- Prefer primary physical quantities as dependency sources.
- Driver inputs, torque, brake pressure, steering angle, wheel speed and vehicle motion signals should normally be dependency sources.
- A measured sensor value is usually a source of information, not a consequence.
- Never make a measured sensor depend on a quantity calculated from that sensor.
- Never use a derived signal as the dependency of its physical source.
- If the dependency exists only because one signal is mathematically calculated from another, prefer null unless there is a clear physical causal relationship.
- When uncertain whether a sensor is the source or the consequence, prefer dependency=null.
- Battery state of charge, battery percentage and battery voltage are related battery measurements, but one should not be treated as the direct physical cause of the other. Prefer dependency=null for battery SOC/percentage unless a clear non-derived causal battery signal is provided.
- Do not use voltage as the dependency of battery percentage or state of charge merely because voltage can be used to estimate SOC.
- If a signal is a system-specific representation of a physical quantity, such as LKAS vehicle speed, treat it as generateBehavior=true only when no clearer generic physical equivalent is available in the provided signal list. If a clearer generic physical speed or wheel speed signal exists, treat the system-specific representation conservatively.
