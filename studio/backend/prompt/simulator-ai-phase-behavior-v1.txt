Compact signal metadata

Each requested signal may contain compact DBC metadata:

* n = exact signal name
* u = engineering unit
* mn = physical minimum
* mx = physical maximum
* f = DBC factor
* o = DBC offset
* b = bit length
* sv = current start value

Always use n as the returned JSON key.

Never use u, mn, mx, f, o, b or sv as part of the signal name.

DBC limits are authoritative.

If mn and mx are provided, every accumulated value for that signal must remain between mn and mx.

If b is 1, the signal is binary and accumulated values must remain only 0 or 1.

If mx is below hundreds of volts, never generate a high-voltage battery value.

If u is rad/s, do not force the value to numerically match km/h speed signals.

If the metadata makes the signal ambiguous or unsuitable for physical behavior planning, omit the signal.

Signal interpretation

* Use only signals present in the requested signal list.
* Not every requested signal needs behavior.
* Returning fewer signals is correct.
* Never invent signals.
* Never rename signals.
* Never guess unknown abbreviations.
* A signal must be generated only if you understand its physical meaning with high confidence.
* If the signal name suggests checksum, CRC, reserved field, set-me constant, diagnostic or protocol bookkeeping, omit it.
* When uncertain, omit the signal.

Phase rules

* Generate behavior for every planner phase.
* Do not create, remove, merge or split phases.
* Use exactly the planner phase ids.
* Every phase must respect driver intent, road type, traffic, weather, road condition, expected stops, expected turns, aggressiveness and speed target.

Behavior objective

For every generated signal:

1. Read its current start value from sv or currentSignalStateJson.
2. Determine the physical objective imposed by the planner.
3. Determine how that signal should physically evolve during the phase.
4. Generate deltas whose accumulated effect reconstructs that evolution while respecting DBC limits.

Delta rules

* Every signal value must be a non-empty numeric array.
* Positive deltas increase the signal.
* Negative deltas decrease the signal.
* Near-zero deltas keep the signal approximately stable.
* Deltas describe behavior transitions, not simulation samples.
* Use smooth profiles.
* Avoid unrealistic oscillations.
* Use the minimum number of deltas required.
* Typical arrays contain 3 to 10 values.
* Maximum array length is 20.
* Never repeat values merely to represent elapsed time.

Physical consistency

Vehicle dynamics must remain physically coherent.

Vehicle speed, wheel speeds, acceleration, accelerator position, brake pressure, torque and steering must describe the same vehicle motion.

During acceleration:

* speed increases
* acceleration is mostly positive
* accelerator generally increases
* torque generally increases
* brake remains inactive

During braking:

* speed decreases
* acceleration becomes negative
* accelerator decreases
* torque decreases
* brake pressure increases
* brake lights may activate if the signal is binary and requested

During cruising:

* speed remains close to the planner target
* acceleration oscillates around zero
* steering remains small unless road geometry requires otherwise

During parking:

* vehicle-motion-related signals progressively converge toward zero
* longitudinal acceleration converges toward zero when the vehicle is stopped
* steering may become larger
* brake activity may increase

Slow-changing signals

Battery percentage, battery voltage, fuel level, temperatures and odometer evolve gradually.

Battery percentage should normally change only by a few percentage points during one hour of typical urban driving.

Battery voltage must remain in the DBC physical range and in the same scale as the supplied start value.

Temperatures change gradually.
